# notesd — Architecture Specification

## 1. Overview

A self-hosted note-taking system: one Go executable backed by SQLite serves a React web client and syncs with offline-first native iOS and Android apps; the web client can keep an offline copy too, by choice. V1 targets a few accounts, such as a family's, each with multiple devices.

| Area | Decision |
| --- | --- |
| Backend | Single Go executable, SQLite (WAL) with FTS5; no external infrastructure |
| Web | React + TypeScript + Tiptap, embedded in the binary; on the server by default, or offline-first like mobile when opted in (§2.5) |
| Mobile | Native Swift and Kotlin apps with local SQLite + FTS5; fully usable offline |
| Documents | Whole Markdown documents in a restricted CommonMark + GFM dialect |
| Sync | State-based incremental replication using per-note revisions and a global change sequence |
| Conflicts | Field-level merge, bodies merged block by block when safe; otherwise a conflict copy |
| Deletion | Permanent tombstones so stale devices cannot resurrect notes |
| Search | FTS5 on every platform, title-weighted BM25 |
| Reliability | Transactional writes, idempotent mutations, crash-safe sync, consistent backups |

## 2. Scope and Requirements

### 2.1 Notes

| Field | Description |
| --- | --- |
| ID | Generated by the client so notes can be created offline; UUIDv7 recommended for chronological ordering |
| Title | Plain text, one line. Editors present it as the first line of the document (Apple Notes style); it is stored and merged as its own field |
| Content | Markdown document |
| Space | The space the note is in (§7.7); `default` unless another is chosen |
| Created at / Updated at | Unix milliseconds, UTC; informational only, never used to order sync |
| Revision | Assigned by the server |
| Deleted at | Optional deletion timestamp |

### 2.2 Editing

Users edit in a WYSIWYG editor and never see Markdown syntax. V1 supports plain text, bold, italic, strikethrough, headings (H1–H3), bulleted and numbered lists, checklists, links, blockquotes and images (§7.6). Attachments and tables are deferred.

### 2.3 Search

- Full-text search over titles and content, with title matches prioritized.
- Case-insensitive, accent-insensitive where supported, prefix matching for search-as-you-type.
- Results show highlighted excerpts; search works offline on mobile.

### 2.4 Synchronization

Sync runs automatically (in the background where the OS allows), resumes after interruptions, tolerates long offline periods, and is idempotent. It must detect concurrent edits and preserve both sides, never resurrect deleted notes, minimize requests and payloads, and never depend on device clocks.

### 2.5 Web application

The web app offers full note management, editing and search. By default it works on the server directly and keeps nothing across browser restarts beyond unsaved edits in memory through transient failures. Opted in ("Keep my notes on this device", at sign-in or in Settings → Sync & data), a browser keeps a full replica and syncs it with the same engine as Android (§3), so it opens, edits, searches and locks notes offline. Signing out, or opting out, removes the replica, asking first if it holds changes the server doesn't have. Browsers without the storage it needs (private windows) aren't offered the choice. Supported: the last two versions of Chrome, Firefox and Safari.

### 2.6 Non-functional requirements

- **Performance:** low idle CPU and memory; thousands to tens of thousands of notes on ordinary hardware. Targets come from benchmarks, not estimates.
- **Reliability:** tolerate server crashes and restarts, network loss, incomplete, duplicate or out-of-order requests, app termination, and devices offline for long periods. Committed SQLite transactions survive process crashes; disk failure or corruption requires a backup.
- **Deployment:** one executable plus a data directory; no separate frontend process. Docker images are optional, never required.

### 2.7 Non-goals for V1

| Excluded | Reason |
| --- | --- |
| Real-time collaboration, CRDTs | One active editor per note; HTTP sync is sufficient. The one WebSocket is for agents and editors (§7.11), not for syncing notes |
| Full version history, merging within a paragraph | Not needed to preserve conflicts; text merges inside a block duplicate and garble prose (§6.2) |
| File attachments | Need their own storage and sync design; images are the exception (§7.6) |
| Sharing single notes between accounts, end-to-end encryption of every note | A space is what's shared (§7.9); per-note sharing would make every note its own boundary. E2EE breaks server-side search. Notes the user locks are the exception (§10.1) |
| PostgreSQL, Redis, external search, job workers, Kubernetes | Unnecessary at this scale |

## 3. Architecture

Three clients talk HTTPS/JSON to one Go server. The native apps keep a local replica; the web client calls the API directly, or, opted in (§2.5), keeps one too.

&#91;embedded content: system architecture · 3 clients, 1 server\]

Every client reaches the server over HTTPS/JSON; the Go binary also serves the web app's build. The native apps, and a browser that keeps its notes, keep working without a connection.

### 3.1 Responsibilities

| Component | Responsibilities |
| --- | --- |
| Go server | Authentication; note CRUD; revision validation and conflict detection; global change sequence; incremental sync; full-text search; serving the web app; database maintenance and backups. Stores whole Markdown documents and never interprets edits. |
| Native clients | Rich-text editing; local persistence and search index; recording pending changes; background sync; conflict resolution; local deletion state; connectivity and sync status. The editor only reads and writes local data; sync runs independently. |
| Web client | Authentication; note listing and navigation; editing with debounced autosave; search; conflict handling; connection and error status. Opted in, the native clients' local persistence and sync too: the sync engine (`shared/sync-engine`), compiled to JavaScript, runs in a worker on sqlite-wasm in the origin's private file system (OPFS), one worker per origin shared by every tab over Web Locks and a BroadcastChannel. The screens read and write through one seam (`NotesSource`): the server's API, or that engine. |

### 3.2 Technology stack

| Platform | Stack |
| --- | --- |
| Backend | Go, `net/http`, SQLite (WAL) + FTS5, JSON over HTTPS, structured logging, web assets via `embed`, systemd or equivalent |
| iOS | Swift, SwiftUI with a `NavigationSplitView` (list and note side by side on a wide window, such as an unfolded iPhone Duo, split at its fold), `UITextView`/TextKit editor via `UIViewRepresentable`, SQLite + FTS5, URLSession, iOS background tasks |
| Android | Kotlin, Jetpack Compose with Navigation 3 (list and note side by side from 600dp, split around a foldable's hinge), `EditText`/`Spannable` editor via `AndroidView`, bundled SQLite + FTS5 (`androidx.sqlite`), OkHttp, WorkManager |
| macOS | Tauri 2 (Rust): a WKWebView window on the server's web app, which keeps its notes there as in Safari (service worker, OPFS); a bundled page picks the server; native menus, links opening in the browser, downloads |
| Web | TypeScript, React, Tiptap/ProseMirror, Vite, lightweight CSS; for the offline copy, the Kotlin core compiled to JavaScript, sqlite-wasm on OPFS, Cache Storage for images and a service worker for the app shell; Node.js only for building |

Native apps use platform controls for selection, keyboard, context menus and formatting. Pick the server's SQLite driver for portability, transaction behaviour and build simplicity, and avoid unnecessary frameworks.

## 4. Data Model

The server holds the authoritative latest state of each note, not a full edit history; mobile devices hold complete replicas plus sync metadata. Two counters must never be confused: the **revision** advances when one note changes, the global **change sequence** advances when any note changes.

### 4.1 Server schema

```sql

    title       TEXT    NOT NULL DEFAULT '',

    moved_to    TEXT                         -- set on a tombstone left by a move to another file (§7.9)

CREATE INDEX idx_notes_updated_at ON notes(updated_at DESC, id DESC) WHERE deleted_at IS NULL;

-- Locked notes' keyring (§10.1): the key wrapped under each secret, and the verifier's hash.
CREATE TABLE lock_keys (id TEXT PRIMARY KEY, kind TEXT, credential_id TEXT, salt TEXT, iterations INTEGER,

CREATE TABLE lock_state (id INTEGER PRIMARY KEY CHECK (id = 1), verifier_hash TEXT NOT NULL);

-- Account-wide settings, such as the time zone agents use for "today".
CREATE TABLE account_settings (key TEXT PRIMARY KEY, value TEXT NOT NULL);
-- Each space's agent (kept when turned off) and its prompt per trigger; both go with the space.

CREATE TABLE agent_triggers (space_id TEXT REFERENCES agent_spaces(space_id) ON DELETE CASCADE, trigger TEXT,
                             prompt TEXT, PRIMARY KEY (space_id, trigger));
-- Agents' runs: queued and running ones are the queue, finished ones the activity log (§7.11).
CREATE TABLE agent_runs (id TEXT PRIMARY KEY, status TEXT, trigger TEXT, space_id TEXT, note_id TEXT, priority INTEGER,
                         event_json TEXT, created_at INTEGER, started_at INTEGER, finished_at INTEGER, failure TEXT,
                         not_before INTEGER, attempts INTEGER, model TEXT, tool_calls INTEGER, prompt_tokens INTEGER,
                         completion_tokens INTEGER, outcome TEXT, message TEXT);
-- Each note a run changed, before its first change and after its last: the diff, and what undo restores.
CREATE TABLE agent_run_edits (run_id TEXT REFERENCES agent_runs(id) ON DELETE CASCADE, note_id TEXT, kind TEXT,
                              before_revision INTEGER, before_title TEXT, before_content TEXT, after_revision INTEGER,
                              after_title TEXT, after_content TEXT, written_at INTEGER, undone_at INTEGER,
                              PRIMARY KEY (run_id, note_id));
-- Tokens per day in the account's time zone, against the daily cap.
CREATE TABLE agent_usage (day TEXT PRIMARY KEY, prompt_tokens INTEGER, completion_tokens INTEGER, runs INTEGER);
-- Writing sessions in progress: a "done" trigger fires 2 minutes after the user's last change.
CREATE TABLE agent_sessions (note_id TEXT PRIMARY KEY, kind TEXT, start_revision INTEGER, last_revision INTEGER,
                             last_user_save_at INTEGER);

CREATE TABLE applied_operations (
    operation_id  TEXT PRIMARY KEY,
    request_hash  TEXT    NOT NULL,
    response_json TEXT    NOT NULL,          -- status code and body, replayed verbatim
    applied_at    INTEGER NOT NULL,
    hash_version  INTEGER NOT NULL DEFAULT 1 -- §4.2
);

```

The tables above are one account's: each account has its own database, `users/<id>.db`, with all of them. Accounts, their sessions and the server-wide settings are in `system.db` (§10):

```sql

-- Only token hashes are stored.

                       csrf_token TEXT, created_at INTEGER, last_used_at INTEGER);
CREATE TABLE settings (key TEXT PRIMARY KEY, value TEXT);  -- email (Resend) key and sender; AI provider
-- Shared spaces (§7.9): their notes, name and icon are in spaces/<id>.db (§7.8); who's in them is here.
CREATE TABLE shared_spaces (id TEXT PRIMARY KEY, owner_id INTEGER REFERENCES users(id), created_at INTEGER);
CREATE TABLE space_members (space_id TEXT REFERENCES shared_spaces(id) ON DELETE CASCADE,
                            user_id INTEGER REFERENCES users(id) ON DELETE CASCADE, joined_at INTEGER,
                            PRIMARY KEY (space_id, user_id));
CREATE TABLE space_invites (id TEXT PRIMARY KEY, space_id TEXT REFERENCES shared_spaces(id) ON DELETE CASCADE,
                            user_id INTEGER REFERENCES users(id) ON DELETE CASCADE, invited_by INTEGER, created_at INTEGER,
                            UNIQUE (space_id, user_id));
-- Moves of notes between files, logged until both files are written (§7.9).
CREATE TABLE space_moves (id TEXT PRIMARY KEY, kind TEXT, space_id TEXT, note_id TEXT, source TEXT, dest TEXT,
                          created_at INTEGER);
```

`notes` has an explicit `INTEGER PRIMARY KEY` rather than relying on the implicit rowid, because `VACUUM` can renumber implicit rowids and silently desynchronize the search index. Migrations are numbered SQL files applied at startup and tracked in `PRAGMA user_version`. The full schema is `server/migrations/` (system.db's in `server/migrations/system/`).

Every mutation, including deletion, increments the note's revision and `current_seq`, updates the search index and records its operation in a single transaction. All writes go through one connection with `BEGIN IMMEDIATE`, so concurrent requests queue in the server instead of failing with `SQLITE_BUSY`; reads use a separate pool and never block on writes. A transactional counter keeps sync cursors aligned with commit order.

### 4.2 Idempotent mutations

Clients attach a unique operation ID to each mutation so retries after a lost response are safe. For each request the server:

1. Looks up the operation ID. If found, it checks the request hash and returns the stored response; a reused ID with a different payload is rejected.
2. Otherwise it validates and applies the mutation, storing the ID and response in the same transaction.

The request hash (version 2) is SHA-256 of the kind of write, the note ID from the path and the body as received, in canonical form: parsed and re-encoded with sorted keys, numbers kept as written. It never depends on the server's own types, so a later release that adds a field to them still recognizes a retry from before. Records from before 1.0 (version 1 hashed the server's decoded struct, which can't be recomputed) match on the operation ID alone.

A client whose retry is refused as reused (`422 operation_id_reused`) sends the change once more under a new operation ID: the revision check (§4.1) turns a duplicate into a conflict or `unchanged`, never a second write.

V1 retains operation records indefinitely; expiring them needs an explicit protocol, since clients may retry at any time.

`notes.updated_by`, `sync_outbox.feed` (`''` for the account's file, else the shared space's id) and `sync_state.user_id` (the account's, from the session) complete it.

Outbox rules:

- A local edit, its dirty flag and its outbox entry are written in one transaction.
- Unsent operations for the same note may be coalesced into one update.
- Once sent, an operation's ID, payload and base revision are frozen across retries. New edits queue as a separate operation until it is acknowledged; it carries the base revision it had when it was first sent, never rewritten afterwards.

### 4.4 Search index

```sql
CREATE VIRTUAL TABLE notes_fts USING fts5(
    title,
    body_text,
    tokenize = 'unicode61 remove_diacritics 2'
);
```

- Holds the plain-text title and text extracted from the Markdown; in V1 the FTS rowid equals the `notes` rowid.
- Kept consistent through triggers or repository code in the same transaction; deleted notes are removed.
- Derived data that can be rebuilt from `notes`. Mobile clients keep equivalent indexes.
- FTS5 availability and identical tokenizer behaviour must be verified on iOS and Android.

## 5. Synchronization Protocol

Notes sync as whole documents over HTTPS/JSON: clients push edits tagged with a base revision and pull changes after a cursor. No keystrokes, editing operations, CRDT updates or persistent connections are exchanged; whole-document sync suits small personal notes with one active editor and is easy to debug.

### 5.1 Uploading changes

On mobile an edit is saved to local SQLite, marked dirty and added to the outbox; the UI updates immediately and the sync engine submits it later.

```http
PUT /api/v1/notes/019a1234

{ "operationId": "019b5678", "baseRevision": 5,
  "title": "Shopping List", "content": "- Milk\n- Bread\n- Eggs", "spaceId": "default" }
```

`spaceId` is optional: absent, a create goes to the default space and an update keeps the note's space (§7.7).

- **Base revision is current** → `{ "id": "019a1234", "revision": 6, "changeSeq": 105, "updatedAt": …, "status": "updated", "spaceId": "default" }`, and the client acknowledges the operation locally. `spaceId` is the space the note is now in, which the client adopts: the one it sent, the default if that space was deleted, or the note's own space for an update that sent none. Identical content and space answer `"status": "unchanged"` without a new revision; a move alone is an update.
- **Base revision is stale** → `409 Conflict` with `{ "error": "revision_conflict", "current": { …latest note… } }`, and the client resolves it as described in section 6. Two more conflict codes use the same shape: `note_deleted` (the note is a tombstone; `current` carries `deletedAt`) and `note_exists` (a create reusing an ID, including a deleted one).
- **Operation already applied** → the stored response, with the header `Idempotent-Replayed: true`. The same operation ID with a different payload is `422 operation_id_reused`, and the client sends the change once more under a new operation ID (§4.2).

**Failed uploads never lose an edit.** Between the app and the server there may be a proxy, an SSO gateway or a Wi-Fi portal that answers in its own way, and a newer server may add error codes. So a change is dropped only when notesd itself says the change can never be accepted: an error body with `invalid_request`, `hash_mismatch`, `image_too_large`, `unsupported_image` or `space_default` (and `not_found` on a delete, which is done). The app keeps the reason to show. Everything else that isn't success, a conflict, a sign-out, a rate limit or `upgrade_required` is *unexpected*: an unknown code, a redirect (API calls don't follow them), a page that isn't notesd's JSON, or a success whose body doesn't decode. The change stays queued and the cycle stops with a message. After 3 unexpected answers for the same change it is *parked*: skipped, so the changes behind it sync, while its note stays dirty and counts as not synced. Parked changes go back in line when the app starts, after a cycle that uploaded something, and when the user taps Retry; one more unexpected answer parks them again. Server errors (5xx) and being offline don't count, since they say nothing about the change.

"Not synced" counts, including the warning before signing out, count dirty notes rather than queue entries. Opening the engine queues a change for any dirty note without one, which also recovers edits that releases before 1.0 dropped.

**Versions.** Apps send `X-Notesd-Client: <platform>/<version>` on every request; the server sends `X-Notesd-Server` on every response and reports its version and `apiVersion` from `GET /auth/status` before sign-in. A server may refuse an app older than a minimum with `426 upgrade_required`; the app pauses sync, keeps every change and asks to update. It never refuses an app that doesn't send the header, so apps from before 1.0, which would treat a 426 as a permanent rejection, are never refused. The minimums are compiled into the server and empty in 1.0. The web app is served by the server it talks to; when `X-Notesd-Server` differs from the version it was built with, an open tab offers to reload. Compatibility rules for later releases are in the [API reference](../reference/api.md#compatibility).

### 5.2 Downloading changes

```http
GET /api/v1/sync?since=100&limit=100
```

At the start of the request the server captures a high-water mark `H` from `current_seq`, then reads within one snapshot:

```sql
SELECT * FROM notes
WHERE change_seq > :since AND change_seq <= :H
ORDER BY change_seq
LIMIT :limit;
```

The response holds the latest state of each changed note (intermediate revisions are skipped; tombstones carry `deletedAt`), plus `nextCursor`, `hasMore` and the server's `generation` (§11.4). Clients send their stored generation back as `?generation=`; a mismatch, or a cursor beyond anything the server issued, answers `409` (`generation_mismatch` / `cursor_ahead`) and the client runs a full reconciliation.

Cursor rules:

1. The client applies a page, preserves any conflicting unsynced edits, and persists the new cursor in the same local transaction before requesting the next page.
2. A crash before commit simply re-downloads the page; duplicate downloads are harmless.
3. When no more changes exist, the server may advance the cursor to `H`, but it must never return a cursor that skips a committed change missing from the response.
4. Sequence increments and note writes commit atomically, so clients never see a sequence number without its note state.

### 5.3 Edits during an upload

An acknowledgment applies to the submitted operation only, never to the current local contents. If the user produces version B while version A is in flight, B stays pending after A is acknowledged, rebased on A's new revision, and A becomes the note's base (`base_title`, `base_content`), so a later merge doesn't mistake A's changes for a conflict. Uploads are serialized per note; different notes sync independently.

An editor open on a note while sync changes it shows the change at once if nothing is being typed; otherwise its next save passes the stored version the typing grew from, and the store merges the two as in §6.1.

### 5.4 Initial sync

A new device authenticates, initializes its database, syncs from cursor 0 in pages, builds its search index and persists the cursor. Notes appear as they arrive, and the process resumes if interrupted.

### 5.5 Scheduling

- Triggers: app launch, return to foreground, local edits (debounced 2 s), opening a note (unless a sync went through in the last 10 s), connectivity regained, OS-approved background windows, periodic refresh while active (every 30 s).
- Failures back off exponentially with jitter; edits never cause one request per keystroke.
- Background execution is not guaranteed on iOS or Android, so correctness must never depend on its timing.
- Web (a browser keeping its notes): the engine's worker syncs on start, 2 s after an edit, on opening a note, when a tab comes back or the network does, every 30 s while a tab is visible and every 5 min while only hidden tabs are open; nothing runs with every tab closed. Opened offline, the page has no CSRF token, so writes wait until the server answers and hands one over; a write is never sent without one.

## 6. Conflicts and Deletion

Accept an edit when its base revision is current, merge automatically when there is no ambiguity, and otherwise keep both versions. Unsynced changes are never silently discarded.

### 6.1 Field-level merge

Title, content and space are merged independently by comparing base, local and server values. A field changed on only one side takes that side's value; a field changed identically on both sides is already resolved. A space changed differently on both sides takes the server's: a move holds no text worth a conflict copy. Content is compared in canonical serialized form, so another client's formatting style (`* item` versus `- item`) does not count as a change. The client submits the merged note against the new server revision and repeats if the server moves again.

| Field | Base (rev 5) | Local | Server (rev 6) | Merged (rev 7) |
| --- | --- | --- | --- | --- |
| Title | Shopping | Groceries | Shopping | Groceries |
| Content | Buy milk | Buy milk | Buy oat milk | Buy oat milk |

### 6.2 Conflicting content

When both sides changed the content differently, the client merges it block by block. `apps/web/src/editor/merge.ts` is the reference implementation; the engine (`BlockMerge.kt`) and iOS (`BlockMerge.swift`) port it, and `shared/markdown-fixtures/merge.json` and `merge-generated.json` pin all three to the same output, byte for byte.

- **Blocks.** Base, local and server are parsed into the editor document (§7.2), and each block list is merged with diff3 (Khanna, Kunal & Pierce): runs where all three agree are kept; between them, a run only one side changed takes that side, and one both changed the same way is taken once. Blocks are matched by a longest common subsequence whose ties go to deleting from the base, so every port pairs them the same way.
- **Both changed one run.** If both sides edited its blocks in place (same count, same kinds), they pair up block by block. If only one did, the other side's added and removed blocks are applied around those edits, unless it removed a block the first side changed. Anything else is a conflict region.
- **Within a block.** A heading's level, a task's checkbox and an ordered list's start number merge as fields (§6.1), separately from text. Lists, list items and blockquotes merge their children recursively. A paragraph's text, a heading's text and a raw block are atomic: changed differently on both sides, they conflict. List numbers are derived on output, so inserting an item never touches the others.
- **Not merged.** Two insertions at the same place, a block moved on one side and edited on the other, or a block whose kind changed (a paragraph made a list item) are conflicts. Nothing merges within a paragraph.
- **Checks.** Each output must serialize back to itself, and no paragraph, heading or raw block may occur more often than in any input; a merge that fails either, or would take more than 4 million LCS cells, is a conflict.
- **Locked bodies** (§10.1) never merge block by block.

The result is one of three:

| Result | What the client does |
| --- | --- |
| Clean | Stores and uploads the merged note, as for §6.1, and records it for Undo |
| Partial: merged except at conflict regions | Two notes, each with every change that merged. The original takes the server's version of each region, the copy the local one |
| Conflict: nothing merged, or a check failed | The server's version keeps the original note; the local version becomes the copy |

A conflicted copy is a new note titled `<Title> (Conflicted copy)` with a new UUID, the local version's space and `conflictOf: <original id>`. It then behaves like any other note. A title both sides changed makes a partial result too, the body merging as above. Every client makes the copy by itself and says so (a notice, and a banner on the copy linking to the original). Only a conflict on the web, with notes on the server, asks the user: **Keep mine** makes the copy, **Use theirs** drops the local edit.

When the editor's save meets a change sync stored meanwhile (§5.3), sides swap: the note keeps the editor's version of each conflict region, and the copy takes the stored one.

**Undo.** A clean body merge can be split back apart for 14 days: the note returns to the version on the side that didn't merge (the server's, or the editor's text for a save, §5.3), unless edited since, and the other version becomes a conflicted copy, what a conflict would have made. The merge is kept in `merge_undo`, one row per note, on the device that merged; the web without a local copy keeps it in the open tab. Deleting or locking the note, and signing out, drop it: a locked note's undo would keep plain text. 14 days stays well inside the 30 a released image is kept (§7.6). Each client shows a banner on a merged note, with Undo.

### 6.3 Crash-safe conflict handling

Creating a conflict copy, adding its creation to the outbox, updating the original note's sync state and recording a merge for Undo commit as one local transaction. A crash before commit leaves the original pending edit recoverable.

### 6.4 Tombstones

Deletion keeps a tombstone (ID, revision, change sequence, deletion timestamp) instead of removing the row; the title and content are cleared. Deleting an already deleted note succeeds (`already_deleted`) without a new revision, whatever base revision the client sends. It increments the revision and change sequence and syncs like any other change. V1 keeps tombstones indefinitely, so the server never tracks per-device acknowledgment and devices offline for months sync normally.

| Situation | Outcome |
| --- | --- |
| Deleted elsewhere, local copy unmodified | Client marks it deleted; the old copy is never re-uploaded |
| Deleted elsewhere, edited offline | Server rejects the edit and the tombstone stands; the edits become a new note titled `<Title> (Recovered copy)` |
| Deleted offline, edited elsewhere | Server rejects the stale deletion; the newer note is kept and the deletion intent is recorded for the user to resolve (Android: the note reappears with a notice that it changed elsewhere) |

### 6.5 Trash (proposed)

A 30-day Trash is recommended but not final. Because tombstones clear content today, adopting Trash means deletion must keep the content until the purge. If adopted, deletion moves a note to Trash, it can be restored while retained, its content is purged after 30 days, and its tombstone stays forever; only then is a scheduled cleanup needed. The alternative for V1 is immediate logical deletion with permanent tombstones.

## 7. Document Format and Editing

Markdown is the stored format for portability and readability; editors work on a native in-memory model and serialize back to Markdown only on autosave, never per keystroke.

### 7.1 Markdown dialect

A restricted, documented dialect based on CommonMark with selected GitHub Flavored Markdown extensions: paragraphs and line breaks, headings, bold, italic, strikethrough, links, ordered and unordered lists, task lists and blockquotes. It is implemented identically on iOS, Android and web. Unsupported constructs must not be silently discarded; V1 editing and import may be limited to the subset.

Images the apps add (§7.6) are first-class. Unsupported constructs (code spans and fences, tables, other images, horizontal rules, raw HTML, and anything else outside the subset) are kept as opaque raw blocks or raw inline runs: shown read-only, not editable, and written back byte-for-byte on save. Turning them into ordinary text is not enough. The serializer would escape their syntax characters and fold their line breaks, so one save on any client would corrupt a note written elsewhere (for example a code fence pasted on another device).

Code fences are the one raw block the web app also writes. It shows a fence's code without the fence lines, with the info string's first word as a language label and syntax highlighting. Typing ```` ``` ```` (optionally with a language) alone in a paragraph and pressing Enter starts a fence, and clicking one opens a code box for its language and code. Leaving the box unchanged leaves the block's source as it was, written back like any other raw block (so only the trailing whitespace §7.4 drops changes); a change writes the whole fence back as ```` ```lang ```` … ```` ``` ````, with a longer fence when the code holds one; a box left with no code removes the block and leaves an empty paragraph in its place. The rest stays read-only. How a fence is split for display is pinned by `shared/markdown-fixtures/fences.json`. Android and iOS show fences the same way (code without fence lines, the language as a label, highlighted, on a dark block) but keep them read-only like other raw blocks; both highlight with the same small keyword scanner (`Fence.kt`, `Fence.swift`), so colours can differ from highlight.js on the web.

### 7.2 Editing model

Markdown is parsed once into the native model (TextKit attributed strings on iOS, spans on Android, ProseMirror on web) and serialized during autosave. Editing must preserve cursor position, selection, undo/redo and active IME composition; saving never rebuilds the editor UI or resets the selection.

The editor document is `title block+`: the note's title is its first line, unformatted and single-line, and the rest is the body. On save the title line becomes the `title` field and the body is serialized to `content`, so the stored note, the sync protocol and the per-field merge are the same on every client. The web app implements this; the native editors follow the same model.

### 7.3 Autosave

- **Native:** debounced local saves, flushed on lifecycle events, keeping the gap to durable persistence short enough to survive abrupt termination. The local database and outbox stay consistent.
- **Web:** debounced HTTP saves, serialized per note so responses cannot arrive out of order. A browser keeping its notes saves to its local database like the native apps, each save based on the text it last stored, so a change sync brought in meanwhile is merged (§6.1).
- **UI states:** unsaved changes, saving, saved, save failed, conflict detected.

### 7.4 Cross-platform consistency

Serialization rules are shared and deterministic for app-produced documents, for example always `**bold**` rather than `__bold__`, and one task-list syntax. Hard line breaks are written as a backslash before the newline (CommonMark), never as two trailing spaces, which editors and tooling routinely strip; serialized output has no trailing whitespace. A shared fixture suite checks semantic round-trip stability across all three editors; byte-for-byte preservation of imported Markdown is not a goal.

Lists, checklists, paragraph styles, cursor behaviour and serialization need substantial custom engineering on top of native text components, so the native editors are prototyped first.

### 7.5 Tags

Tags are plain text in the note, as in Bear: there is no tag field, so tags sync, merge and conflict with the text that holds them, and no protocol or document-format change is needed. Every platform derives them with the same extractor, pinned by `shared/markdown-fixtures/tags.json`; editors only style them.

- **Syntax:** `#tag`, or `#multi word tag#` closed by a `#` that follows a non-space and ends a word. `/` nests to any depth: `#home/repairs`, `#school projects/biology 101#`.
- **Where:** the title (plain text) and every body line except fenced code. A tag starts at the beginning of a line or after whitespace, `(`, `[` or `{`; `# Heading` is a heading, `C#` and URL fragments are not tags. Code spans, links, images and autolinks never hold tags; emphasis does not interrupt them.
- **End:** a one-word tag ends at whitespace or punctuation other than `-`, `_` and `/` (`#one,` is `one`). A multi-word tag stays on one line.
- **Numbers:** a one-word tag made only of digits, `-`, `_` and `/` is not a tag (`#1 priority`); `#2024#` is.
- **Identity:** levels are trimmed, inner spaces collapsed and empty levels dropped; the key is the result lowercased. A note lists each key once, with its first spelling; across notes, a tag is named as in the most recently updated note using it.
- **Hierarchy:** `#a/b` implies `a`. Filtering by a tag includes its nested tags; counts are distinct notes.
- **Lifetime:** a tag exists while a live note uses it.

Renaming and deleting tags (rewriting every note) are not implemented yet.

### 7.6 Images

An image lives outside the note's text, as a content-addressed blob on the server; the note holds an ordinary Markdown image pointing at it:

```markdown
![alt text](notesd:image/<sha256 hex>?w=1600&h=1200)
```

- **Reference.** The hash is SHA-256 of the bytes as stored, so uploads are idempotent and integrity-checked. `w` and `h` are the pixel size, so editors lay the image out before its bytes arrive. Editors show such an image as an atomic, read-only node (deleted whole) and write its source back byte for byte; any other image (`![a](cat.png)`) stays a raw inline run (§7.1). Search, previews and tags treat it like any image: its alt text is plain text and never holds tags.
- **Preparing.** Clients downscale before uploading: the long side is capped at 2048 px, orientation is applied, and the image is re-encoded as JPEG (quality 0.85), or PNG when it has transparency, which drops EXIF metadata including location. GIFs are uploaded as they are, so animation survives, along with any metadata they hold. The server caps an image at 10 MiB; clients cap a prepared one 28 bytes lower, the nonce and tag encryption adds, so it fits locked or not.
- **Uploading.** The web app uploads before it inserts the reference. Android stores a new image locally with a pending-upload row, and each sync cycle uploads pending images before any note operation, so no device sees a reference before its bytes exist.
- **Caching.** The web relies on the browser cache (images are immutable); a browser keeping its notes stores images in Cache Storage instead, per account: one added there waits as a `pending_images` row until sync uploads it, before any note showing it, and others are downloaded on first view and kept. Android fetches an image the first time it is shown and keeps it in its cache directory, which the system may evict; images still waiting to upload live in its files directory.
- **Locked notes.** A locked note's images are encrypted too (§10.1). Whether to decrypt is decided by the blob's type as served, not by the note, so a note that mixes both still renders.
- **Storage.** Blobs are rows of the server's SQLite database (`images`), so a backup of the one file holds notes and images consistently.
- **Export.** `notesd export` writes each image a note shows once, as a plain file in `images/<id>.<ext>`, and points the reference there (only image syntax; the same text inside code is left alone). Locked images are decrypted with the lock password under `--include-locked`; one that is missing or doesn't open keeps its `notesd:image/` reference.
- **Import.** `notesd import` stores the JPEG, PNG, WebP and GIF files imported notes show as they are, up to 10 MiB, without the clients' downscaling or re-encoding. It reads `w` and `h` from the file, swapped when a JPEG's EXIF orientation turns it sideways.
- **Deletion.** The server records which live notes show which images (`note_images`), in the transaction that writes the note. A plain note's references are read from its content; only image syntax counts, so a reference inside code is not one. A locked note's come from the `imageIds` its client sends with the save, since the server can't read the ciphertext: the web app lists them on every locked save; Android lists them for each recent body it encrypted or received, including when sync later sends that body in a merge or a conflicted or recovered copy. Notes, sync changes and conflict answers carry a locked note's recorded `imageIds`, so a device that can't read a body still knows its images. A locked update without `imageIds` (a body the device can't read) leaves the record as it was. An image no note shows is *released*: at upload, and when the last note showing it drops it or is deleted. One released for 30 days is deleted, by a job `serve` runs every 6 hours, or by `notesd gc-images`. The 30 days cover undo, conflicted and recovered copies (§6.2, §6.4) and devices that were offline. Uploading an image again restarts its 30 days, so a picture added back isn't collected before its note saves. Images stored before references were tracked are released only once a note has shown and dropped them, except plain ones no plain note shows, which the backfill releases. A note from a device offline for longer than 30 days can still point at a deleted image; it shows as missing. `notesd check` reports references to missing images.

### 7.7 Spaces

Spaces keep separate contexts, such as Work and Personal, apart: each note is in exactly one, and the list, tags and search show the current space only. They are not folders: there is no hierarchy, and a note never has to be filed. Tags (§7.5) stay the way to organize within a space.

- **Default.** Every install has the space `default`, created as "Notes" by the migration. It can be renamed but never deleted. A fixed id lets every device file notes before it first downloads the list. The sidebar always names the space shown, atop it; the name opens the switcher (below), and New space is also in Settings. With only this space there are no other space actions (no Move to space, no matches from other spaces).
- **Ids and names.** Clients choose space ids (UUIDv7), so a space can be created offline. Names are trimmed, inner whitespace collapsed, 1–64 characters, unique ignoring case: a name another space has gets " 2", " 3"… appended by the server (the name shortened to fit 64), which settles two devices creating "Work" offline. Renames are last-writer-wins. Lists show the default space first, then the others by name.
- **Icons.** Each space has an icon, chosen with its name when it's created and changed with it later. It is a key (`[a-z0-9-]`, up to 64) into a set of full-colour pictures the apps ship (`scripts/space_icons.py` generates each app's copy from the web's SVGs); the server stores it without knowing the set. `''` is the app's own icon: the default space's until someone picks another, offered first in the picker, and shown for any key an app doesn't have, so an app can drop an icon but never rename a key. The sidebar shows the space's icon instead of the app's mark: the default space's icon already is it. The list's title leads with the space's icon too, so the space shows with the sidebar away (on the web, not while the sidebar is beside it). A `PUT` without `icon` keeps the space's icon; the native apps always send it, so a space's name and icon are last-writer-wins together.
- **Themes.** An icon comes with a theme, never chosen apart from it, so where you are shows at a glance. Its tinted neutrals (background, paper, ink) carry the mood; its accent shows in few places: the caret, checked tasks, the main button, and links. Each theme is a seed in `scripts/space_icons.py`, which derives every token from it once, moving any that falls short of WCAG contrast (4.5:1 for text; 3:1 for the caret, a control's edge and the focus ring) until it passes. Button labels are checked against their fills but never moved: one that can't pass means changing the seed. If any colour can't pass, generation stops without writing anything; otherwise it writes them for each app: on the web, `styles/space-themes.css`, applied with `data-space` on `<html>`; on Android, `ui/SpaceThemes.kt`, which `NotesTheme` turns into the `Tokens` of the space shown (the editor's View-drawn spans read them as they draw); on iOS, `UI/SpaceThemes.swift`, whose values `Palette` (`UI/Theme.swift`) resolves through a `SpaceThemeTrait` set on the window and bridged to SwiftUI's environment, so a sheet can preview another theme. The app icon's theme is the app's colours from before themes, and an icon an app doesn't have gets it too. Themes are display only: nothing is stored beyond the icon.
- **The list syncs whole.** Like the keyring, clients download `GET /spaces` on every sync cycle. The native apps keep a local copy: a create or rename marks its row dirty and a delete marks it pending; each cycle sends those (`PUT`/`DELETE /spaces/:id`, both idempotent, so no operation ids) before downloading the list, takes the name the server stored, and replaces every row that isn't waiting to be sent.
- **Deleting.** Only an empty space can be deleted, never the default (`409 space_not_empty` with its `count`, `409 space_default`). A device whose delete is refused because notes arrived from elsewhere drops the pending delete, and the space comes back with the next list.
- **Notes.** A note's space is a field like its title (§2.1), plaintext even when the note is locked. A note that names a space that no longer exists (filed offline into a space deleted elsewhere) is stored in the default, and the write's answer says so. Moving a note between spaces in the same file is an ordinary update; into or out of a shared space it's a move between files (§7.9). Conflicted and recovered copies keep the local version's space.
- **Switcher.** Where you are, then where you can go. Anchored under the name on the web and on Android's wide layout; a bottom sheet on Android phones and iOS. Top to bottom:
  - a card for the current space: its icon and name, a line per trait (§7.8) worded by its label and summary, or by its problem in the danger colour, and Info, to its Space info. A space without traits gets no line: private is the default and goes unsaid, as sharing is one feature among many;
  - invitations into other people's spaces, each with Join and Decline in place, only when there are any;
  - "Switch to": the other spaces in list order, the current one left out (it's the card). Each row is one line: icon, name, then its trait glyphs. A second line only for something to look at: what others changed there while this account was away (with a dot after the name), else its traits' problems in the danger colour. Each row also opens that space's Space info without switching: an ⓘ on hover or keyboard focus on the web (always shown on touch), a long-press on phones. Left out with one space;
  - New space.

  Invitations and changes come from sharing (§7.9).
- **Current space.** Each device has its own, never synced. It is the default at a cold start (a page load on the web), and again on returning after more than 30 minutes in the background, unless a note is open in the editor. Switching clears the list's tag, Untagged or Locked filter. New notes, including from launcher shortcuts, go to the current space.
- **Search.** Searching covers the current space; the first page also counts the matches in all the others (`otherSpaces`), shown as a last row that lists them (`?exceptSpace=`). Opening one switches to its space.
- **Export.** With more than one space, `notesd export` writes each note into a folder named after its space, with `images/` shared beside them; with one it stays flat. The shared spaces the account is in are exported with its own (§7.9).

### 7.8 Space traits

Features that act on a whole space (sharing, publishing, agents) are its *traits*: on or off for the space, never for a note. Every app shows them the same way, so a person learns once how to read what a space does, and every new feature fits the same places.

- **What one is.** A key, a monochrome glyph the apps draw, a label ("Shared"), a one-line summary of its state ("With Ana and Ben"), its settings, and its *exposure*: the sentence saying who else can see the space's notes ("Visible to Ana and Ben", "Public at …"), absent when the trait keeps them to the account.
- **Order.** Fixed, never the order they were turned on: `shared`, `published`, `agent`, later ones appended. The server sends them in this order and the apps show them as sent. A key is reserved in the order before its feature ships, so traits never change places between releases.
- **Where.** Wherever an app shows a space, its traits follow: the sidebar's switcher, Move to space, Settings › Spaces and search's other-spaces row after the name; the list's title, which shows the space's icon but not its name, after the icon, but only while the sidebar is away: with the sidebar docked beside the list, its switcher shows them and the title doesn't repeat them. The glyphs are packed (no empty slots), in the tertiary ink; beside the switcher and the list's title they're grouped in one filled button that opens Space info. A space with no traits looks as it did before traits existed. The switcher (§7.7) is where the glyphs get their words: its card gives each trait a line; its rows show only the glyphs, named in each row's accessible label. iOS menus draw one image per row, so Move to Space lists the traits' labels as the row's subtitle instead.
- **Colour.** Glyphs are monochrome; one turns the danger colour only when its trait has a problem (publishing failed). Colour means "look at this", never "this is on". Activity (another member's edits) is a separate signal and never mixes with the glyphs.
- **Space info.** Each space's one page of space-level settings, and everything on it is changed in place: nothing opens over it, so what a change did shows where it was made. On the web it's one wide dialog, held near the top so it grows downward; on iOS, one sheet; on Android, one screen. A trait may have one page of its own, for settings that would crowd the rest (publishing's Customize site): a row in its section, summarising what's set there, opens it in place of the rest, in the same dialog, sheet or screen, never over it. On the web the dialog's height springs to the new page's (none with reduced motion), focus goes to the page's title and comes back to the row, Escape and Back return to the rest, and what's typed on the page is kept until Space info closes. Top to bottom:
  - its icon, name, note count and trait glyphs. For its owner the name is edited where it's shown (saved on Enter or leaving the field, put back with Escape or when emptied) and the icon, pressed, opens the picker under the header, each pick saved as it's made with the page taking its theme. A glyph that turns on while the page is open arrives with a little movement, seen as it starts to mean something;
  - a section per trait the app knows, in order, when on or when the feature can be turned on: the trait's own (sharing's is People, §7.9), with everything it changes in it, turning on included, since a feature is turned on by using it (inviting someone shares a space), not by a switch. A trait without a section of its own is a row with its label and summary, or its problem in the danger colour; one this app doesn't know says to update the app;
  - Delete, for the owner, with Done.

  Destructive actions (removing someone, handing the space on, stopping sharing, leaving, deleting) confirm under the button that asked, in the danger tint, saying what will happen, focus on Cancel, Escape closing only the confirmation; iOS uses its confirmation dialog, anchored where it was asked. That button opens it (the name opens the switcher), as do the switcher's Info and each of its rows' ⓘ or long-press, and each row of Settings › Spaces. It is the only place a space-level feature is configured.
- **Crossing the boundary.** Moving a note into a space asks first when the destination exposes it to someone its current space doesn't reach: the dialog lists the exposure sentences of the destination's traits whose `audience` has a key the current space's traits don't (a trait without an `audience`, from a newer server, is compared by its sentence). Moving between spaces that expose the same, or into one that exposes less, doesn't ask; neither does creating a note in a space.
- **Wire.** Spaces from `GET /spaces` and `PUT /spaces/:id` carry `traits`: `[{ "key", "label", "summary", "exposure"?, "audience"?, "problem"? }]`, `[]` for a space with none. The server works them out from each feature's own state (a `spaces.TraitSource` per key, registered on the account's store); clients never send them. `audience` comes with `exposure`: who it reaches, as stable keys (`user:<id>`, `public`), so a move compares people rather than wording. A list from a server older than traits has no `traits`, read as none.
- **Unknown keys.** An app shows a trait it doesn't know with a generic glyph and the server's label and summary, and asks before a move by its exposure, so an older app never hides that a newer server shares or publishes a space. Its Space info row has no settings and says to update the app.
- **Sync.** The native apps keep each space's traits on its row. Every list download replaces them, even on a row whose rename is still waiting: traits are the server's, not the device's.
- **Locked notes.** A locked note is only its account's to read (§10.1), so a space refuses locked notes while any trait exposes it to someone else. Each feature tells the server, whoever asks, whether its trait exposes a space (a `spaces.ExposureSource`, registered with the trait); no feature has its own rule for locked notes.
  - The server refuses a locked body bound for an exposed space, created, edited, locked or moved there (`422 locked_in_exposed_space`), checked in the write's transaction.
  - Turning on what exposes a space (an invitation, publishing) is refused while the space holds locked notes (`409 space_has_locked`, with their `count`). The space's file is held for writing while the locked notes are counted and the feature records its state (`notes.Store.WithoutLocked`), so none can be locked in between.
  - The apps keep Lock where it always is and, chosen in a space with a trait that has an `exposure`, explain instead, worded by the first such trait: "Locked notes can't be in a shared space", with its exposure ("Family is visible to Ana"). Moving a locked note there explains the same way.
  - A note locked offline in a space exposed meanwhile from another device is refused when it syncs: the device keeps the locked version as a recovered copy in the default space and puts the note back as the server has it.
- **Storage.** Two kinds of data, in two places, for every space-level feature:
  - *What the space is and how its features act on it* (its name and icon, a feature's settings) is in the file holding the space's notes: the account's for one of its own spaces, `spaces/<id>.db` for a shared one (§7.9). It moves with the notes when a space is shared, and backup, export and removal stay per file.
  - *What leads to the space* (who reaches it: owner, members, invitations; anything else the server needs before it knows which file to open) is in `system.db`. A row there that names a file says `user:<id>` or `space:<id>`, as `space_moves` does.
- **Adding a trait.** Reserve the key in `spaces.TraitOrder` and every app's registry; register its `TraitSource` where the account's stores are built (`userdata`), and, if it lets others read the space's notes, its `ExposureSource` (`Spaces.AddExposure`) wherever the space's file can be, or the space keeps accepting locked notes; give each app's registry entry its glyph, its label (Space info names a trait that's off, which the server doesn't send), its Space info section (everything it changes, on or off, in place), and whether it can be turned on. The switcher, Space info and the move check come from the shared pieces and need no change.

### 7.9 Shared spaces

A space's owner shares it, with every note in it, with other accounts on the same server. Sharing is per space, never per note: what you share is a boundary, and everything filed there is shared with it.

- **Roles.** The account that shares a space is its *owner*; everyone who joins is a *member*. The owner invites and removes members, cancels invitations, renames the space, changes its icon, deletes it and hands ownership on; members read and edit every note and can leave. Only the owner can do the first group (`403 not_space_owner`). The default space is never shared, so everyone always has a private one.
- **Storage.** A shared space is its own database file, `spaces/<id>.db`, with the same tables as an account's (§4.1); its `spaces` table holds only that space, with its name and icon, which the owner's renames write (§7.8). Its owner, members and invitations are in `system.db`. The space keeps the id it had, so its notes keep their `space_id`. Revisions, change sequences, the sync generation and images are per file, as for accounts.
- **One address.** Clients never learn which file a note is in. Every request but a feed's goes to the account's address and the server picks the file: a write or `GET /notes/<id>` finds the note among the files the account reaches (where it's live, else where it was deleted); a create goes to its space's file; `?space=` on the list, filters and search reads that space's file. Only a shared space's change feed has its own address (`/spaces/<id>/sync`), since each file has its own sequence; it checks membership (`404 not_found` otherwise). A note moved only to files the account doesn't reach (another member moved it into their own space) is deleted as far as it can tell: `GET` answers `410` and an update `409 note_deleted`, with the tombstone without `movedTo`, and a delete `already_deleted`.
- **Sharing.** The first invitation makes a space shared: the server moves its live notes and the images they show into the new file, with the same ids and revisions, leaves a moved tombstone of each in the owner's file, and deletes the space's row there. It refuses the default space (`409 space_default`) and a space holding locked notes (`409 space_has_locked`, with their `count`). The space stays its own file for good: once every member is gone and no invitation is pending it is private again (no trait), without moving back.
- **Moves between files.** An update whose `spaceId` is a space in another file moves the note there, with the update's text, as one write: the base revision is checked where the note is, and the answer is the revision in the destination. That keeps the note's revision for a move alone and takes the next for changed text, or one past the destination's tombstone of the note if that is higher. The images it shows are copied there; so is any image an update shows that only another file the account reaches has, since pictures are uploaded to the account's own address. The source row becomes a moved tombstone. A retry is answered by the file that recorded its operation id, wherever the note is now. A note filed offline into a space shared since simply lands in that space's file.
- **Crash safety.** A move, a space's or one note's, is logged in `system.db` (`space_moves`) before the destination is written. The source's write transaction is held from reading the notes until their tombstones commit, so nothing changes in between, and one move runs at a time, so two in opposite directions can't deadlock. At startup, before any request, a logged move is finished if its destination stored the notes (the source's become moved tombstones) and dropped if it didn't (a space's half-made file is deleted); a space counts as stored once `shared_spaces` has it, which is written in the same step.
- **Moved tombstones.** A tombstone left by a move has `deletedAt` and `movedTo` (the destination space). A device that syncs the destination's feed keeps the note, and that feed brings its revision there; one that doesn't (a member, after a note was moved into someone's own space) removes it like a deletion. A move into a file where the id is a moved tombstone revives that row. A write that meets a share or move that ran after it chose its file starts over, up to three times, then answers `503 busy`, which clients retry like any server error.
- **Feeds.** A device syncs one feed per file it can reach: the account's (`/sync`) and one per shared space it's in (`/spaces/<id>/sync`), each with its own cursor, generation and full reconciliation (§5.2, §11.4). A note's feed follows its space: a space the list marks `shared` is its own feed, the rest are the account's. Each cycle downloads the space list and invitations, adds a feed for each shared space new to the list and drops the feed of one no longer in it (its notes, queued changes and merge records leave the device), uploads, then downloads the account's feed and each shared one. Uploads go to the account's own address; `GET /images/<id>` there finds an image in any file the account reaches, so pictures load from one address.
- **Uploads.** One queue for every change, sent to the account's address whatever space the note is in (the server finds the file). Moving a note into or out of a shared space is an ordinary update; a device only re-files the note's row under the destination's feed.
- **Moved tombstones on a device.** One from a feed the note no longer belongs to here (the destination's feed came first, or the move was this device's) is ignored. Otherwise, if the device syncs `movedTo`'s feed, the note takes that space and keeps its text until that feed brings it; if not, it's a deletion (§6.4), a recovered copy keeping any unsynced edit. A move into one of the account's own spaces is followed only when the account made it (the tombstone's `updatedBy`): another member's move to their own space can name an id every account has, such as `default`.
- **People.** Space info's section for sharing (§7.8): who's in the space (the owner first, "You" marked), who's invited (an outlined avatar, Cancel beside it), then everyone else on the server, each invited with one press, their row arriving in the list above with a brief highlight. A space no one else is in says what inviting does instead of listing only its owner. The owner removes someone or hands the space on from their row and stops sharing under the list; a member sees the list and Leave.
- **Invitations.** The owner invites from the accounts on the server (`GET /people`: ids and usernames, readable by any account). An invitation waits in the invitee's switcher (§7.7, from `GET /invites`, read every cycle) until they join or decline; joining switches to the space and starts its feed from cursor 0. There are no notifications or emails.
- **Leaving.** A member leaves, or the owner removes them: the space leaves their list, and their devices drop its feed and its notes. A note there with changes not yet synced becomes a recovered copy in the default space first: being removed, or the space being deleted, comes with no warning on the device, and a bad list must never cost an edit. The owner can't leave: they hand ownership to a member (`PUT /spaces/<id>/owner`) or stop sharing by removing every member. Removing an account hands each space it owned to the member who joined first; a space left with no member keeps its file on disk for the host, as a removed account's does.
- **Last editor.** Every note records the account that last changed it (`updatedBy`, set by the server from the session, in every file; a device sets it to its account, `userId` from the session, on its own edits). Note rows show "Ana · 2h" and the editor "Edited by Ana" only when it wasn't you, by username from the space's member list; an account no longer in it shows nothing.
- **What changed.** Each device keeps when the account last opened each space. The switcher (§7.7) marks a shared space with a dot and a line such as "Ben edited 3 notes · 2h", counting notes others changed since. It's device-local and never synced.
- **Trait.** `shared` (§7.8) is on while the space has another member or a pending invitation. Its summary is from the viewer's side: "With Ana and Ben", "Invited Ana", "With Ana · invited Ben"; its exposure names everyone else, members and invited: "Visible to Ana and Ben".
- **Space list.** `GET /spaces` lists the account's own spaces and the shared ones it's in, the default first, then by name. A shared one adds `shared`: `{role, members: [{id, username}]}`, plus `invites: [{id, userId, username}]` for its owner. Names are unique among an account's own spaces only: a shared space may have the same name as one of a member's own.
- **Locked notes.** None while anyone else is in the space or invited: the trait exposes it, and the rule for exposed spaces applies (§7.8). Every invitation counts the space's locked notes first (`409 space_has_locked`), the first one too, before anything moves. A shared space with no one else in it and no invitation exposes nothing, and takes locked notes like any other.
- **Export and mirror.** Each member's `notesd export` and Markdown mirror (§11.1) include the shared spaces they're in, as folders like their own.

### 7.10 Published spaces

A space's owner can publish it as a small website, by analogy with HEY World: every note with a title and a body is a post, and the site has a list of posts, tags, a feed and a search, with nothing to set up first. Publishing is a trait (§7.8), `published`, separate from sharing: a space can be both, and then every member's notes in it are public too.

- **Who.** An account publishes its own spaces; a shared space's owner publishes it, like renaming it (`403 not_space_owner` for members). The default space can't be published (`409 space_default`): every account keeps one space no trait exposes, where a locked note refused elsewhere is kept (§7.8).
- **Locked notes.** Publishing exposes the space to anyone (`audience: ["public"]`), so the rule for exposed spaces applies (§7.8): refused while it holds locked notes (`409 space_has_locked`), and no locked note can be written there while it's published (`422 locked_in_exposed_space`).
- **Own domain.** A site can have a domain (`domain`, `blog.example.com`; `published_spaces.domain`). notesd doesn't route by `Host`: the owner's reverse proxy maps the domain onto `/@<handle>/` (Caddy's `rewrite * /@<handle>{uri}`, nginx's `proxy_pass …/@<handle>/`), so only the site is reachable there, and the proxy gets its certificate as it does the app's. notesd builds the site's absolute links (`url`, the feed, sitemap, canonical and Open Graph URLs, the trait's summary) from `https://<domain>/` instead. For a site to work at any path, nothing in it names `/@<handle>/`: pages link relatively, the redirect from an old post address is relative (`./<slug>-<short>`, set by hand since `http.Redirect` makes it absolute), and the 404 page, served at any depth, has its root filled in for each request.
- **Address.** `/@<handle>/` on the app's own origin. The handle (`a-z`, `0-9` and `-`, 1–64 characters, not starting or ending with `-`, unique on the server) comes from the space's name ("Garden Notes": `garden-notes`, `-2` when taken) and can be changed; renaming the space doesn't change it. A post is `/@<handle>/<slug>-<short>`: the slug from its title, the short id 8 hex digits of its id's SHA-256 (more if two collide). Only the short id identifies the post, so an address made before a title changed redirects (`301`) to the current one. The server never learns its public address (§10), so the app sends its origin when it publishes (`origin`), and the feed and sitemap's absolute URLs are built from it, unless the site has a domain of its own (below), which they're built from instead.
- **Storage.** By §7.8's rule: the address (`file`, `space_id`, `handle`, `origin`, `domain`, `published`) is in `system.db` (`published_spaces`); the space's own settings (its custom CSS, `space_publish`) are in the file with its notes, and move with them when the space is shared, while the share rewrites the address's `file` in the transaction that records it. Turning publishing off keeps the row (`published = 0`), so the handle stays the space's; deleting the space frees it. Deleting an account frees its own spaces' handles; a shared space it owned keeps its address, as the space goes to the member it's handed to (§7.9).
- **Posts.** A live note with a title and a body (neither blank), newest first by creation time; its page shows when it was written, and when it was updated if on a later day. The site is live on save: a note to draft first is written elsewhere and moved in.
- **Rendering.** The editor's Markdown (§7.1) through goldmark with GFM, raw HTML escaped and unsafe link schemes dropped. The note's title is the page's only `<h1>`, so body headings step down a level. Images the apps added are copied into the site and sized from their reference (`w`, `h`), loading lazily; any other image shows its alt text. `#tags` link to their pages, found by the same scanner as the apps' tags (§7.5) with each tag's position in the text. Excerpts are the plain text (§8.1), cut at a word near 200 characters.
- **Pages.** Home lists posts with excerpts, 30 to a page (`/`, `/page/2/`…); a post's page has its tags and the newer and older posts; `/tags/` is every tag as a tree with its count (a nested tag counts in its parents), and each tag has a page of its posts, nested tags' included, all on one (a tag's `page/2/` would be the address of a tag nested in it); `/feed.xml` is an Atom feed of the newest 50 in full; `/sitemap.xml`; `/search?q=` (below). Pages are plain HTML and CSS; one small script, in `<head>` so a page never flashes the other theme, keeps a light or dark pick in the browser, and pages follow the system's preference without it.
- **Look.** The site has the app icon's neutrals in every theme with the space's accent (from its icon; the icon itself isn't shown), checked by `scripts/space_icons.py` for contrast on those neutrals (links 4.5:1, the accent 3:1) in light and dark (`publish/assets/theme.css`). Like notesd's own pages, a sticky bar runs along the top with the accent on its top edge and the page blurred under it. Titles, headings and quotes are in Instrument Serif, the face the apps title notes with, served by the site itself (latin and latin-ext subsets, regular and italic, about 67 KB in all, content-named and cached for good; OFL, `publish/assets/fonts/`); dates and a post's reading time (230 words a minute) are small mono capitals. The accent also marks selected text, list markers, link underlines and tag pills. Each body heading gets an id from its words and a link to itself; excerpts leave out `#tags`. The favicon is an SVG of the name's first letter on the accent, light or dark with the browser (`look.go`, from `assets/accents.json`, which the same script writes); it's the one response whose CSP allows an inline style. Pages carry Open Graph tags for link previews and cross-fade where the browser supports view transitions, unless reduced motion is asked for. The markup is semantic and shallow, with classes named for what they hold (`site-header`, `post`, `post-title`, `post-list`, `post-item`, `excerpt`, `tag`, `tag-tree`, `pager`, `search-form`…). The owner may add custom CSS (up to 64 KB): the site's own styles are in `@layer notesd`, so the custom CSS, appended unlayered, wins without `!important`, and most changes are a variable (`--bg`, `--surface`, `--text`, `--muted`, `--border`, `--accent`, `--link`, `--font-body`, `--font-heading`, `--font-mono`, `--measure`). Its `@import`s are moved to the top, where CSS reads them.
- **Serving.** A publisher in the server renders each site into files under `data/public/<handle>/`, with a manifest mapping each address to its file; requests are answered from those files, never building a file name from the URL, and never reading the database. A site is rendered when it's published and at startup, then again once its notes have been quiet for 10 seconds, or at most 2 minutes after the first change; only files that changed are rewritten, the manifest too, each replaced whole. Pages are `Cache-Control: public, max-age=60, stale-while-revalidate=86400` with an ETag; images, the stylesheet and the script are named by their content and cached for a year (`immutable`); HTML, CSS, XML and the script are stored gzipped too. Public responses never read or set a cookie, so a CDN or proxy may cache them, and carry a content security policy allowing only the site's own script. `data/public/` is derived: backups can leave it out, and it's rebuilt at startup.
- **Search.** The one dynamic page, and the only one that reads the database: FTS5 over the space's notes (§8), showing only what the site publishes, through a pool of 2 read connections to the file of its own, so searches never take the apps' connections. A few searches run at once (as many as the CPUs, at least 2), beyond which it answers `503` with `Retry-After`; each visitor (their address, or the one a proxy on a private address forwarded) may search 30 times a minute (`429`); answers are kept for a minute; results pages are `noindex`.
- **Trait.** `published`: summary "At notes.example/@garden", exposure "Public at notes.example/@garden", audience `public`; problem "Publishing failed" when the last render failed.
- **Apps.** The web app's Space info (the Mac app's too: it opens the server's) has a Published section (`settings/published-space.tsx`). Off, its owner publishes, sending the app's own origin. On: the address, its handle edited in place (asked first: the old address isn't redirected); Customize site, the section's page (§7.8), its row summarising what's set there; and Stop publishing. Customize site has the custom CSS, saved when Save is pressed, and the domain, saved the same way, asked first when emptied. For the domain the app says only what the proxy maps it onto (`/@<handle>`, with Copy) and links to the user guide, which has the steps for Caddy, nginx, Cloudflare Tunnel and other proxies: a proxy's setup is the docs' to keep, not the app's. A member sees the trait's summary. Every app shows publishing turned on or off at once: the space list carries the expected trait ("Publishing…" until the server gives its address) before the call returns, put back if it fails, and dropped once the list agrees. Turned off, the trait leaves the glyphs at once but still refuses locked notes until the server confirms (`Space.leaving`), since a note locked in between would be refused. On the web, each call syncs a device's own copy before reading the list again, as sharing does. Android's has the same section without Customize site, which is the web's to change (`sharing/PublishedSection.kt`): Publish, sending the address the app reaches the server by (`ApiClient.origin`), then the address with Open, Share (the system's sheet) and Change address (asked first), and Stop publishing; each call syncs after, so the trait and its lock rules arrive with the space list. iOS's is the same (`Settings/PublishedSection.swift`, `ApiClient.origin` in NotesCore), its handle a field in the form, Change Address asked in a confirmation dialog. In development, Vite proxies `/@<handle>/` to notesd like `/api`, leaving its own `/@vite/`, `/@fs/` and `/@id/`.
### 7.11 Agents

A space can have an agent: prompts the user writes, run by a model on the server when something
happens to a note. It acts through tools on the notes in its own space and never sees a locked one.
The user guide is [agents](../guides/using/agents.md).

- **Provider.** One OpenAI-compatible chat completions API per server, set up by an admin
  (`internal/llm`). The key stays in system.db. Test asks the model to call a tool; agents need
  one that does.
- **Triggers.** The notes store's in-transaction write hook (`notes.Store.OnWrite`) queues runs, so a
  trigger commits or rolls back with its write. A delete queues *note deleted* with the note's last
  title and content, since the tombstone has neither; a move queues *moved out* (as it left) and
  *moved in*. A create or edit starts or extends a writing session (`agent_sessions`); the runner
  ends it 2 minutes after the user's last change and queues *new note done* or *note edit done*
  for the space the note is in then, or at once when an editor closes the note and the server has
  what it last saved (`editor.closed` on the socket below). A note moved to or from a shared space's
  file (§7.9) reaches the hook as a move too: the file it left queues *moved out* and drops its
  session, the file it came to *moved in*. Never a trigger: the agent's own writes and saves holding
  only its change, unchanged saves, writes sent with `X-Notesd-Sync` (a device's first sync, an import),
  locked notes, and conflicted or recovered copies.
- **Socket.** `GET /api/v1/agent/socket` is a WebSocket (`coder/websocket`) behind the usual
  authentication; a browser session also needs a same-origin `Origin`, since a cross-site page can
  open a WebSocket with the cookie and no preflight. Each web tab keeps one open while the space it shows has its
  agent on, and says which notes its editor opens and closes; leaving for a space without one, it
  closes once the open note has said it closed. The server pings every 25 seconds,
  under proxies' idle timeouts (nginx: 60); net/http clears the server's timeouts on the upgraded
  connection. A hub (`internal/editors`) keeps each account's connections, at most 50.
- **Runner.** One worker per account runs its queue in order, editor triggers first, one run at a
  time, so one at a time per note. It sleeps until a write queues a run or starts a session, or
  the next of those is due. At most 4 provider calls run at once across accounts. With AI
  removed the queue waits. A run is told notesd's instructions, the space's prompt and the trigger's
  prompt, which stay the same from run to run so the provider can cache them, then the event: the
  time in the account's time zone and the note. Each run logs where its time went: waiting, getting
  ready, the model's calls and the tools'.
- **Tools.** Read: `get_note`, `search_notes`, `list_notes`, `list_tags`, `get_cursor`. Write:
  `set_title`, `edit_note` (find must match exactly once), `insert` (start, end or the cursor),
  `set_content` (a note's whole content, for one the agent keeps, like a digest; not made again to a
  note changed since), `create_note`. A write can carry `done`, the run's summary: the run ends with it, without a model call just
  to say so. Nothing deletes, moves or locks a note, or leaves the space; locked notes are left
  out of every listing and search, not only hidden from reads. Writes go through the store as
  ordinary updates marked `agent: {runId, only: true}`, based on the revision the run read. If the note
  changed since, the change is made to it as it is now, without starting over; one that no longer
  fits (a find the user changed) comes back to the model with the note as it is now. The run's own
  note deleted, moved or locked meanwhile stops the run. Its writes are the account's
  (`updatedBy`, §7.9), so "Edited by" never names anyone else for them.
- **In the editor.** A note an editor has open on the socket is read from it instead: unsaved
  typing and the cursor included (`internal/editors`; the run's own editor first, else the one that
  opened it last). A write to it is worked out on the server as above, then sent as before and
  after, with the change as the agent asked for it; the editor applies it if it still shows before,
  else makes the change itself to what it shows (only one that no longer fits, a find typed over, makes
  the run read it again), as one step
  the user can undo there, and saves it as any edit, with the text its Markdown writes (which the
  run then records). The edit is recorded with no `after_revision` until a save holding exactly
  what the run left arrives. That save is the agent's alone, and fires nothing, if the server held
  exactly what the editor showed before the run's first unsaved change (kept as a hash,
  `applied_from`, not text); otherwise the user's unsaved typing went out with it, and it counts
  as theirs too. A save with typing after the change isn't linked, so undo can't take that
  typing; the edit then can't be undone from Activity (`not_saved`). An editor that doesn't answer within 10
  seconds counts as gone: a read falls back to the store, a write fails the run
  (`editor_disconnected`).
- **Limits.** 20 tool calls, 150,000 tokens and 5 minutes per run; a daily token cap per account
  (1,000,000 unless the admin sets one), which also stops a run that reaches it. Each call's tokens
  are counted as it returns, so a crash can't spend tokens the cap never saw. A provider failure is retried once after 30 seconds if the
  run changed nothing. The queue holds at most 500 runs per account.
- **Record.** Each run keeps its status, tokens, the model's last line or why it failed, and for
  each note it changed the text before and after (`agent_run_edits`), written in the same
  transaction as the change. A finished run drops the note's body from its event, and its title
  too for a *note deleted* run or a note since deleted, as the tombstone did. Locking a note
  clears its body from every run's copies (and skips its queued runs); deleting it clears title
  and body. On a delete, a queued or running run keeps its event's snapshot until it ends, since a
  *note deleted* or *moved out* run needs it; locking clears it at once, whatever the run's status.
  A run checks before each model call that its note isn't locked, deleted or moved (unless that was
  its trigger), and stops if it is. Finished runs are deleted after 30 days.
- **Activity and undo.** `GET /agent/runs` lists runs with their edits; a run's detail diffs
  each note line by line (Myers, after trimming the common start and end), computed on read.
  Undo writes each edited note back, and deletes each note the run created, based on the
  revision the run left, marked as the agent's alone so it fires nothing, with a fixed operation id so a
  retry replays; a note changed, locked or deleted since is skipped. The run's outcome becomes
  `undone`, or `partly_undone` while some of its changes stand.
- **Trait.** `agent` (§7.8) is on while the space's agent is on and has a prompt. Its summary names
  the moments it has prompts for ("While you write · when you’re done"). Its exposure is the AI
  provider ("Sent to the AI at api.example.com", audience `ai:<host>`): moving a note into the space
  asks first, since its notes go there. With no AI set up it has no exposure and its problem is
  "AI isn’t set up". The agent is set up from its row in Space info, the trait's settings; Turn on is
  offered once AI is set up, or to resume a paused agent.
- **Own spaces only.** Agents run in an account's own spaces, never a shared one (§7.9): a shared
  space's file has no agent store and its writes reach no hook, its setup is `404 not_found`, and a
  space whose agent is on can't be shared (`409 space_has_agent`); a paused agent goes with the
  space's row when it's shared. Shared spaces would need their own answers first: whose AI settings
  and token cap a run uses, who sees its Activity and can undo it, and where its setup is kept.

## 8. Search

Every platform uses SQLite FTS5: mobile searches its local database with no network, and the web app calls `GET /api/v1/search` on the server, or searches its own copy when it keeps one.

### 8.1 Indexed content

A locked note (§10.1) contributes its title only: its body is ciphertext, so it has no excerpt, preview or body tags on any platform.

The index holds titles and plain text extracted from Markdown, so formatting never affects results (`This is **important**.` is indexed as `This is important.`). Extraction preserves word boundaries and follows the same rules on server and mobile, checked with shared fixtures. Each note mutation updates the index in the same transaction, and the index can be rebuilt from the notes table without touching sync state. Tags (§7.5) are indexed alongside, in `note_tags`. A migration that changes derived data asks for a rebuild, which the server runs at startup.

### 8.2 Ranking

BM25 with per-column weights, title 10.0 and content 1.0:

```sql
SELECT n.id, n.title,
       snippet(notes_fts, 1, '<mark>', '</mark>', '…', 20) AS excerpt
FROM notes_fts
JOIN notes n ON n.rowid = notes_fts.rowid
WHERE notes_fts MATCH ?
  AND n.deleted_at IS NULL
ORDER BY bm25(notes_fts, 10.0, 1.0)
LIMIT 30;
```

This weights relevance rather than forcing every title match above every content-only match. If strict title-first ordering is required, add an explicit title-match tier.

### 8.3 Queries and results

- Results update as the user types, with a short debounce and FTS5 prefix queries.
- FTS5 queries are built safely from user input and parameterized, never interpolated; malformed syntax never surfaces as a user-visible error.
- Each result returns `id`, `title`, a highlighted `excerpt` and `updatedAt`; deleted notes are excluded and the server caps result counts. The server's excerpt is HTML-safe: note text is escaped and matches are wrapped in `<mark>`, so the web app can render it directly.
- Query building is uniform: the input is split into words, each becomes a quoted prefix term, and terms are ANDed. FTS5 operators in user input are inert.
- On mobile, results reflect local edits immediately, before they sync.

| `PUT` | `/api/v1/spaces/:id/owner` | Hand a shared space to another member |
| `GET` | `/api/v1/spaces/:id/sync` | A shared space's change feed (§7.9); everything else about its notes is at the account's address |
| `GET` | `/api/v1/invites` | Invitations waiting for this account |
| `POST` | `/api/v1/invites/:id/accept`, `/decline` | Join a shared space, or decline |
| `GET` | `/api/v1/people` | Every account's id and username, to invite |
| `GET` `PUT` `DELETE` | `/api/v1/spaces/:id/publish` | How a space is published; publish it or change how (`handle`, `origin`, `css`); take its site down (§7.10) |
| `GET` | `/@:handle/…` | A published space's site, for anyone (§7.10) |
| `PUT` | `/api/v1/images/:sha256` | Upload an image (raw body); idempotent, the hash must match (§7.6) |
| `GET` | `/api/v1/images/:sha256` | Download an image, cached as immutable |
| `GET` | `/api/v1/locks` | The locked-notes keyring (§10.1) |
| `PUT` `DELETE` | `/api/v1/locks/keys/:id` | Add, replace or remove a keyring entry; needs the verifier |
| `DELETE` | `/api/v1/locks` | Forget the keyring after a forgotten lock password; needs the account password |
| `GET` | `/healthz` | Process health |
| `GET` | `/readyz` | Database readiness |

- Create, update and delete accept operation IDs for retry-safe mutations.
- Validation errors, authorization failures and revision conflicts use clear, consistent response shapes.
- Note listing (`?limit=50`) returns list fields only: ID, title, created and updated timestamps, revision and a plain-text preview (one line per block, at most 160 characters). Mobile apps build lists locally.
- Errors share one shape: `{ "error": code, "message"?, "field"?, "current"? }`.
- The authoritative, up-to-date reference is `server/README.md`; the OpenAPI document in `shared/api/` is still to be written.
- Listing and sync use cursor pagination; sync cursors are based only on server-assigned sequences, never offsets.
- Search queries are parameterized, validated, limited and paginated.
- Emailing sends the server's copy, not the client's: the request carries the revision the client shows, and a different one is `409 stale_revision`, so the client syncs first and the email matches what the sender saw. Browsers can't call Resend directly, and one key serves every device.
- Major versions are explicit. Mobile apps may stay outdated for long periods, so breaking changes to note format, sync semantics or authentication need a compatibility strategy.

## 10. Security

An installation holds a few accounts, such as a family's, each signed in from multiple devices. Accounts share whole spaces with each other (§7.9). Accounts have no roles beyond admin; a shared space has an owner and members.

- **Isolation:** each account's notes, search index, sync state, spaces, locked-notes keyring and images are in its own SQLite file, `users/<id>.db`; a shared space's are in its own, `spaces/<id>.db` (§7.9). A request's session and path pick one file, the account's or a shared space it's a member of, and handlers only ever see that one, so a missing check can't expose another account's data. Ids, image hashes and sync generations are per file. Backup, export and removal are per file too.
- **Accounts:** the first is created at first run (below). Admins add the rest from People in the web and Android apps (`POST /users`), or the host with `notesd add-user`; there is no sign-up and no email. An invited account has an empty `password_hash` and can't sign in until its one-time setup link (`setup_links`, SHA-256 of the token, 7 days, one per account) is used to choose a password. The same link, made for an account that has a password, is the apps' password reset; the host's is `notesd reset-password --username`. The server never learns its public address: the app that asked builds the link from its own (the web app's origin, Android's server address: `<address>/setup#<token>`, the token after `#` so it stays out of logs). Removing an account (People, or `remove-user`) deletes it and its sessions and leaves its notes file for the host to export or delete.
- **Profiles:** each account may choose a display name and a photo, both optional; without them the apps show the username and its initial. They're about who someone is, not their notes, so they live in `system.db`, not the account's notes file or the sync feed, and change through plain endpoints (`/profile`). Everyone signed in sees everyone's, as they see usernames to share spaces: members, invitations, "edited by" and the invite list name people by their chosen name, with their photo. The photo is served by account id with its version in the URL, cached for good. The apps crop it to a square of at most 512 px and send a JPEG; the server decodes it and encodes it again, so EXIF (a phone's location) and anything else in the file is dropped. An invitation may carry the admin's suggested name, which the invitee confirms or changes on the setup page.
- **Admins:** the first account is an admin; People or `add-user --admin` makes others. Only admins change server-wide settings (the email and AI integrations), which every account uses, and manage accounts. The server enforces it (403 `admin_only`), keeps one admin who can sign in, and doesn't let an admin change their own account from People.
- **Devices:** a signed-out device keeps its notes, and its first sync under another account would upload them there (a different sync generation means full reconciliation, §11.4). So the apps let only the same account sign in again; switching accounts means removing all data first. The web app removes its copy on sign-out and keeps a database per account, so neither applies there.

- **Credentials:** username and password, hashed with Argon2id (parameters encoded in the hash so they can be raised later); never stored in plaintext. Password changes are supported and sign out every other session. Failed logins are rate-limited (10 per 15 minutes per client address).
- **First run:** while no account exists, `POST /auth/setup` creates one for whoever calls it first, with no token, and every client's onboarding goes straight to creating the account, except the iPhone's: App Store guideline 5.1.1(v) requires an app that creates accounts to delete them too, which notesd doesn't do, so the iPhone app sends the person to a browser. After that the endpoint returns `already_set_up`. The server logs a warning with its address until the owner exists. The cost: a server reachable from the network before its owner exists can be claimed by a stranger. The default listen address is loopback, so a fresh install isn't reachable, and the hosting guide says to create the account before exposing it; on a hosting platform (`$PORT`) it's public from the start, accepted to keep one-click deploys free of setup. To skip the open window entirely, `NOTESD_OWNER_USERNAME` and `NOTESD_OWNER_PASSWORD` create the owner at startup (ignored once one exists), or `notesd create-owner` creates it from the shell. A claimed server holds no one else's data, and deleting the data directory starts over. That's why tokenless setup is acceptable here (the same trade-off Coolify and Jellyfin make).
- **Web sessions:** an HttpOnly, SameSite=Lax cookie (`Secure` and `__Host-` prefixed when the request came over HTTPS, directly or per the proxy's `X-Forwarded-Proto`; a request's cookies under either name are each tried, so a hop that drops the header doesn't sign anyone out and a stale one under the other name can't shadow a valid one; sign-out clears both) with a 30-day sliding expiry, plus a CSRF token the web app keeps only in memory and sends as `X-CSRF-Token` on every mutation; cross-origin `Origin` headers are rejected (the request's `Host` and `X-Forwarded-Host` count as same-origin). A session that ends while a browser keeps its notes pauses sync and asks to sign in again; local notes stay readable, as on mobile.
- **Browser copies:** a browser that keeps its notes stores them in plain text in its origin storage (locked notes and their images stay encrypted), readable by anyone using that browser profile, which is why it's opt-in and worded "on a device you trust". The app asks the browser to persist the storage; without that, the browser may clear it under pressure, and with it any edits not yet synced. Each account has its own database file and image cache; signing out removes them.
- **Mobile sessions:** a one-hour access token and a 180-day sliding refresh token, sent as bearer tokens and kept in the iOS Keychain or Android Keystore-backed storage. Refresh tokens are not rotated, so a refresh whose response is lost can be retried; revocation deletes the session. Only token hashes are stored server-side. Session expiry affects sync only, never access to local notes.
- **Transport:** HTTPS for any remote access; TLS may terminate at any common reverse proxy. Private-network and VPN-only installations are supported.
- **Encryption:** no at-rest encryption; users may rely on disk encryption. Documentation must state that the server can read note content, except for locked notes (§10.1), which are end-to-end encrypted. Encrypting every note would affect search, authentication and the data model, so it remains a separate decision.

### 10.1 Locked notes

Like Apple Notes' locked notes: the user locks chosen notes, and their bodies are encrypted on the device with a key the server never has. Titles stay readable, so the list, title search, title tags and the title merge are unchanged.

**What protects what.** The server, its database, its backups and anyone reading them see only a locked body's ciphertext; its title, dates, size and title tags stay readable. The one exception is `notesd export --include-locked`, which the owner runs on the server's machine with the lock password; it decrypts notes and their images locally into the export folder, and the password and key exist only in that process. A device that is unlocked (key in memory) and the person holding it see everything. The web app is served by the server it distrusts, so a tampered server could serve code that captures the lock password; the native apps don't share that weakness. Text a note held before it was locked was stored in plain text and survives in backups made before then. In the live database the server scrubs it: SQLite runs with `secure_delete`, the FTS5 index with its own `secure-delete` option (otherwise deleted terms stay in its segments until a merge), and the save that locks a note is followed by a `wal_checkpoint(TRUNCATE)`, so the WAL's older page images go too. That checkpoint gives up while a long read still holds old pages, which later checkpoints then overwrite. Free disk blocks, file-system snapshots and SSD wear-levelling are outside SQLite's reach.

**Envelope.** A locked note's `content` is one line, `notesd:locked:v1:` + unpadded base64url of a 12-byte nonce, then AES-256-GCM ciphertext and tag of the UTF-8 Markdown body, with additional data `notesd:locked:v1`. The note ID is not bound in, so conflicted and recovered copies (new IDs) stay readable. Being locked is a property of the content, like tags (§7.5): no new note field, and the sync protocol, revisions, outbox and tombstones are unchanged. Locking and removing the lock are ordinary updates.

- **Versions.** Any content starting with `notesd:locked:` is locked; the next segment is its version (`v1`). Every client and the server recognize the whole family, so a later format can't be mistaken for plain text, edited, indexed, emailed or have its images collected by an older release. A client that doesn't know the version opens the note read-only and asks to update. The server stores an unknown version as an opaque locked body if it is `notesd:locked:v<n>:` + one line of base64url, and refuses anything else. Locked images do the same with their type: `application/vnd.notesd.locked` is v1, later versions are subtypes (`application/vnd.notesd.locked.v2`), never parameters.
- Clients never re-encrypt unchanged text: an open note keeps the envelope it was stored as and replaces it only when the decrypted text changes, so the server's `unchanged` status and byte comparisons stay meaningful. A retried operation resends the same envelope (an operation ID's payload is fixed, §4.2).
- The server checks only shape (prefix, one line of strict base64url, length), which is enough to refuse an edit made on the ciphertext as if it were text. The 1 MiB content cap applies to the plain body: an envelope may be as long as that of a 1 MiB body.
- Merging (§6.1) compares envelopes as stored, never in canonical Markdown form, so sync merges without the key: a body changed on one side takes that side; changed on both, the local version becomes a conflicted copy, still locked. Locked bodies never merge block by block (§6.2), on any client.
- Locked notes are excluded from search text, previews, excerpts and body tags (§8.1), and the server refuses to email them (`409 note_locked`).
- A locked note's images (§7.6) are encrypted with the same key: `nonce ‖ ciphertext ‖ tag` of the image file, binary, with additional data `notesd:image:v1`, uploaded as `application/vnd.notesd.locked`. The image type is recovered by sniffing after decryption. Locking a note re-uploads each of its images encrypted and rewrites the references before the save; removing the lock does the reverse. If an image can't be fetched (offline and not cached), the change is refused rather than leaving a locked note pointing at plain images. The old blobs are released and deleted after 30 days (§7.6). Until then the plain copies of a newly locked note's images stay readable on the server, as do the plain images in backups made before. The `imageIds` a locked save lists tell the server which encrypted blobs belong to which locked note; it learns nothing of their content, and their sizes were already visible.

**Keys.** Each account has one 32-byte locked-notes key, created by the first device to lock a note. The server keeps a keyring of wrapped copies, each AES-256-GCM of the key under a key-encryption key, with additional data `notesd:lnk:v1:<kind>`:

| Kind | Key-encryption key | `kdf` |
| --- | --- | --- |
| `password` (exactly one) | PBKDF2-HMAC-SHA256 of the NFC-normalized lock password, 600,000 iterations, 16-byte salt | `{"name":"pbkdf2-sha256","iterations":600000}` |
| `recovery` (optional) | PBKDF2 of a random 120-bit code shown once, 10,000 iterations | `{"name":"pbkdf2-sha256","iterations":10000}` |
| `passkey` (any number) | HKDF-SHA256 of the WebAuthn PRF output, info `notesd:passkey:v1`; the entry's 32-byte salt is both the PRF input and the HKDF salt | `{"name":"hkdf-sha256"}` |

Each entry records its key derivation in `kdf`, with its parameters; entries from before 1.0 have it filled in from their kind. Clients derive with the function `kdf` names, and one they don't know is reported as "update notesd", never as a wrong password; the server refuses to store a name it doesn't know, so an entry is never kept under an assumed function. A later move to Argon2id is a new `kdf` name, adopted by re-wrapping on the next password change.

The GCM tag doubles as the wrong-password check. Changing the lock password re-wraps the key; no note is re-encrypted. PBKDF2 rather than Argon2 because WebCrypto and the JVM both have it built in.

**Passkeys** (web). Adding one asks for the lock password, since the browser's copy of the key can't be read back out to wrap it again. The server never verifies an assertion: a passkey that can't produce the PRF secret simply can't unwrap anything. Authenticators without PRF support are refused when added. A passkey belongs to the server's domain, so moving the server to another address leaves its passkeys unusable (the password still works).

**Fingerprint** (Android). The key is sealed with a Keystore key that needs a strong biometric for every use and is destroyed when enrolled biometrics change; the sealed copy stays on the device. It is kept against the password entry it was made with: when that entry changes (a new password from another device, or a reset) fingerprint unlock turns itself off and the password is asked for, so a stale key never encrypts new notes. A password change on the same device keeps it on, since the key is unchanged. The first time the lock password is typed on a phone (creating it or unlocking), the fingerprint prompt follows straight away to turn it on; "Not now" or turning it off in Settings stops that offer, and it comes back once fingerprint unlock goes stale or the account signs out. It can't be on by default: the Keystore key only takes the locked-notes key after a fingerprint check.

**Face ID** (iOS; Touch ID where the iPhone has it). The same rules as fingerprint unlock. The key is kept as a Keychain item whose access control needs Face ID for every read (`.biometryCurrentSet`, so it's unreadable once enrolled faces change) and which never leaves the device. Face ID scans as soon as it's asked for, which leaves no "Not now" in its prompt, so the offer after the lock password is the app's own question first; Face ID then confirms before the key is stored.

The keyring syncs to the native apps on every cycle and is kept locally, so locked notes open offline. Changing it needs a **verifier**, HMAC-SHA256 of the key with `notesd:verifier:v1`, whose SHA-256 the server stores with the first entry: a stolen session alone can't replace or delete the wraps and strand the notes. Forgetting the keyring after a forgotten lock password needs the account password instead; notes locked under it can then never be opened.

**Unlock session.** The key lives only in memory, as a non-extractable `CryptoKey` on the web. It is dropped after five minutes idle, when the web tab has been hidden for five minutes, when the Android app leaves the screen, on sign-out, and on request; edits to open locked notes are saved (encrypted) first. Android keeps locked notes out of screenshots and the recent-apps thumbnail while one is open.

Shared vectors in `shared/crypto-fixtures/locked.json` (generated by `scripts/crypto-fixtures.mjs`) pin key derivation, wrapping, envelopes and the verifier on every platform.

Status: built are the envelope, the keyring and its endpoints, the lock password on the web, Android and iOS, passkeys on the web, fingerprint unlock on Android and Face ID unlock on iOS. iOS can't block screenshots, so it covers an open locked note in the app switcher instead. The recovery code is still to be built (the server and every client's crypto already accept `recovery` entries).

## 11. Deployment and Operations

Production needs one executable, a writable data directory and an open HTTP port; schema migrations run automatically at startup.

### 11.1 Running the server

```text
notesd
data/
    system.db    # accounts, sessions, server-wide settings, shared spaces' members
    users/1.db     # one notes database per account
    spaces/<id>.db # one per shared space (§7.9)
    public/<handle>/ # published spaces' sites, rendered from the databases (§7.10)
    *.db-wal       # runtime files, may not exist
    *.db-shm
```

```bash
./notesd --data-dir /var/lib/notesd --listen 127.0.0.1:8080
```

Configuration is flags and environment variables (`NOTESD_DATA_DIR`, `PORT` (the hosting-platform convention: listen on every interface at that port, unless `--listen` is given), `NOTESD_LOG_LEVEL`, `NOTESD_LOG_FORMAT`, `NOTESD_OWNER_USERNAME` and `NOTESD_OWNER_PASSWORD` for first-run owner creation, `NOTESD_MIRROR_DIR` for the Markdown mirror (below), and `NOTESD_RESEND_URL` for tests); a config file is not planned unless the option count grows. Subcommands: `create-owner`, `add-user`, `list-users`, `remove-user`, `reset-password`, `reindex` (rebuild the search index), `check` (integrity check), `gc-images` (delete images no note has shown for 30 days), `export`, `version`; `backup` is still to be built (§11.4). Targets: Linux x86-64 and ARM64 (including Raspberry Pi 5), small VPS installs and home servers. Docker images are optional.

**Markdown mirror.** `serve --mirror-dir DIR` keeps every account's live, unlocked notes in `DIR/<username>/` as files laid out like `export`'s, always with a folder per space, so a second space doesn't move every file (`internal/mirror`). It is low priority and one-way. A committed write to an account's notes, spaces or images flags that account, without blocking; one to a shared space's file flags each of its members, and joining, leaving, removal and renames flag the members concerned. One goroutine writes an account once it has been quiet for 10 s, or 2 min after its first unwritten change. It reads what changed from the sync feed (§5.2), from a cursor kept in a manifest (`.notesd-mirror.json`) beside the files, together with the path and hash of each file it wrote. The shared spaces an account is in (§7.9) are read too, each from its own feed and cursor, into a folder of their own; a note's file is removed only by the feed that wrote it, so a note that moved between files is never deleted by the one it left, and leaving a space removes its notes' files. So a restart resumes, an unchanged note isn't rewritten, and only the mirror's own files are ever replaced or deleted. A new sync generation (a restore, §11.4) rewrites the folder and drops files of notes the database doesn't have. Spaces aren't in the feed, so each pass compares their names to their folders; a renamed space's folder moves whole only when it holds nothing but the mirror's files. Names that would clash are compared ignoring case on every filesystem, since the folder may be synced to macOS or Windows. A manifest path that isn't a plain relative path refuses the folder, since a synced manifest could come from elsewhere. Files are replaced through a temporary file and a rename. A note that is locked loses its file, so its plain text doesn't outlive the lock on disk. A note showing an image not yet uploaded is written again once the image arrives.

WAL mode is enabled with a busy timeout for brief write contention. The development toolchain and build tasks are defined in the root `mise.toml` (`mise run build` produces the binary with the web app embedded). Installation, HTTPS and systemd are covered for users in `docs/guides/self-hosting/`; releases (server binaries and the signed APK) in `docs/contributing/releasing.md`.

### 11.2 Process supervision

systemd is recommended; the unit users install is in `docs/guides/self-hosting/binary-systemd.md`. The server shuts down gracefully on termination signals so transactions complete or roll back.

```ini
[Service]
User=YOUR_USERNAME
ExecStart=/usr/local/bin/notesd serve --listen 0.0.0.0:8080 --data-dir /var/lib/notesd
StateDirectory=notesd
StateDirectoryMode=0700
Restart=on-failure
```

### 11.3 Self-healing

| Failure | Recovery |
| --- | --- |
| Server crash or unclean shutdown | Supervisor restarts it; SQLite rolls back incomplete writes and startup proceeds normally |
| Network loss | Apps keep working offline; pending changes stay in SQLite and retry with idempotent operation IDs |
| Interrupted sync | Cursor advances only after changes are applied; sync restarts from the last committed cursor |
| Database corruption | `PRAGMA integrity_check` via an admin command; failures logged clearly; the database is never deleted or replaced automatically |

### 11.4 Backups and disaster recovery

Client replicas are not a backup. `notesd backup /path/to/backup.db` uses SQLite's online backup API or an equivalent consistent snapshot; copying the live file under WAL is not safe. Backups plug into restic, Borg, systemd timers, NAS jobs or object storage, and off-device copies are strongly recommended.

Restoring an older backup leaves clients with newer revisions and cursors than the server. The server therefore keeps a persistent **sync generation ID**, which clients store with their cursor. When it changes, clients run a full reconciliation instead of incremental sync, preserving unsynced edits and never treating missing notes as deleted. Status: the generation exists in `sync_state`, is returned on every sync page and is checked when sent back; changing it on restore (and the `backup` command itself) is still to be built and tested before backup restoration is called reliable.

On Android, full reconciliation re-downloads every note and compares text rather than revisions: a note whose text matches is adopted at the server's revision; one the server lost or holds an older text of is re-sent; one the server no longer has is re-created. Progress is stored (`full_sync`, `full_sync_seen`), so it survives the app being killed halfway. One gap remains until the server marks restores: a note edited on the restored server whose revision is still below the device's is overwritten by the device's re-upload.

### 11.5 Health monitoring

`/healthz` confirms the process is running and `/readyz` that the database is reachable. Neither exposes application data; both work with systemd, Gatus, Uptime Kuma and similar tools.

### 11.6 Resource efficiency

- Avoid long-lived per-device connections, permanent background workers, in-memory copies of the database, full histories, external dependencies and polling jobs that scan every note.
- Keep transactions short, indexes limited to listing, sync and search, and skip Markdown parsing on reads.
- Sync transfers only changed notes, each in full, with HTTP compression where useful; diffs are excluded from V1.
- Tune and test the Go runtime on memory-constrained systems.
- Images live outside note content, content-addressed for deduplication and integrity (§7.6); ones no note has shown for 30 days are deleted. Deleted rows are zeroed (`secure_delete`) and their pages reused; the file doesn't shrink without a `VACUUM`.

## 12. Testing Strategy

Testing emphasizes failure scenarios over happy paths, with multiple simulated clients running independently against a shared server.

### 12.1 Synchronization scenarios

| Scenario | Expected result |
| --- | --- |
| Single device edits | Successful sync |
| Two devices edit different notes | Both changes preserved |
| Two devices edit different fields | Safe merge |
| Two devices edit different blocks of the content | Merged, Undo offered |
| Two devices edit the same block | Conflict copy, with every other change in both notes |
| Request succeeds, response lost | Idempotent retry |
| Client crashes during download | Resumes without skipping changes |
| Client crashes during conflict handling | Pending edits preserved |
| Note deleted on another device | Tombstone applied |
| Deleted note edited offline | Recovered copy |
| Offline deletion conflicts with newer edit | Newer content preserved |
| Device offline for months | Successful sync |
| Server restored from backup | Safe reconciliation |
| Same note edited during upload | Later edits stay pending |
| Two accounts edit a shared note's different blocks | Merged for both |
| A note moved into or out of a shared space while another device is offline | The offline device's edits follow the note, or become a recovered copy if it left their reach |
| Server stops in the middle of sharing a space or moving a note | Startup finishes or undoes the move; no note in two files, none lost |
| A member is removed while offline | Their devices drop the space on the next sync |

Property-based, randomized tests should generate arbitrary sequences of edits, deletions, disconnects, retries and reconnects, then assert that no unsynced user content disappears silently.

### 12.2 Other suites

- **Web replica** (Vitest, the engine in-process on in-memory sqlite-wasm against a real server; Playwright in Chromium, Firefox and WebKit): the screens on the local copy, merges and conflicted or recovered copies, locked notes and images offline, opening offline from the service worker and the copy, a session ending under sync, tabs handing the engine over without losing a call, opting in and out.

- **Backend** (temporary SQLite databases): note CRUD, revision conflicts, deletions, transaction rollback, sequence allocation, pagination, search indexing, duplicate operation IDs, migrations, authentication.
- **Editors** (shared fixtures across web, iOS and Android): formatting selections, including across paragraphs; lists; nested formatting; undo/redo; cursor preservation; Markdown round trips; Unicode, emoji and right-to-left text; multiline selections; IME composition.
- **Performance** (thousands to tens of thousands of notes, on modest hardware): idle memory, startup time, note create and read latency, large-collection sync, search latency, database growth, mobile battery impact.
